<objective>
Put every driver behind one interface and one event sink, so adding a provider
in Phase 3 changes neither the web UI, nor the SSE stream, nor the terminal
mirrors.

Today the choice is an `if (backend() === 'codex')` branch inside
`server/src/agent.ts` `runTurn`, and each of the two paths calls `emit`,
`emitUpdate`, `emitEphemeral` and its own copy of an idempotent `endTurn` guard
directly. The shared bookkeeping around them — echoing the learner's message,
`turn_start`, draining pending notices, assembling the instructions, the `active`
and `stopping` maps, `cancelPending` — is already shared and stays shared. This
plan replaces the branch, not the bookkeeping.

The proof that the seam works is a third driver that is not a real provider: a
`fake` driver that scripts a sequence of sink calls and resolves. It is a
permanent fixture, and it is what makes the phase's third success criterion
testable without a model, a login or a network.

Purpose: FOUND-03, and the foundation Phase 3's owned loop plugs into.
Output: one interface, one sink, three implementations, one test.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| provider SDK -> event sink | model-authored text and tool-call metadata cross into Derive's event log and from there into the browser and the Obsidian mirror |
| driver -> database | a driver that wrote directly to the DB would bypass the one place redaction and ordering are enforced |
| test fixture -> production path | `setDriverOverride` is an injection point reachable at runtime |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | `setDriverOverride` | medium | mitigate | the override is set only from test code and is never wired to an environment variable, a request header or a config file; the production dispatch reads `backend()` as it does today. Confirm no route or env var can set it |
| T-04-02 | Spoofing | an event emitted outside the sink | medium | mitigate | after task 3 the only turn-end emitter inside the seam is the sink; the verify step greps both driver files for it |
| T-04-03 | Information disclosure | provider text reaching the event log | high | transfer | the single sink is exactly the chokepoint plan 01-08 wires redaction into; concentrating every driver's output here is what makes that one change sufficient |
| T-04-04 | Denial of service | a driver that never resolves | medium | accept | unchanged from today — the SDK's own timeouts and the learner's Stop are the controls; the `active` map and `interrupt()` still work through `ctx.onActive` |
| T-04-05 | Repudiation | a turn with no turn_end | medium | mitigate | the sink's idempotent guard plus the existing finally block guarantee exactly one `turn_end`; the fake-driver test asserts it for a driver that reports nothing at all |
| T-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | this plan adds no dependency; manifests and `pnpm-lock.yaml` are untouched. If execution finds it needs a package, stop and raise it rather than installing |
</threat_model>
