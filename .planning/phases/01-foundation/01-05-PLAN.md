<objective>
Give the database a real migration path, and make the two destructive writes
atomic.

Today `server/src/db.ts` opens SQLite at import time and runs an inline
`CREATE TABLE IF NOT EXISTS` block followed by a try/catch list of `ALTER TABLE`
statements — the "SQLite has no ADD COLUMN IF NOT EXISTS" idiom. It works, but
nothing records what schema a given file is on, nothing is transactional, and a
failed change is indistinguishable from a column that already existed.
Meanwhile CONCERNS.md records `replaceGraph` and `deleteLesson` running their
multi-statement work with no transaction at all, so a crash mid-plan-approval
leaves a partial graph and a crash mid-delete leaves orphan events and nodes
with no lesson row.

This plan installs a numbered runner on `PRAGMA user_version` with the existing
block folded in verbatim as migration 1 — verbatim is load-bearing, because it
is what makes an upgraded database and a fresh one converge on identical schema
— then wraps the destructive writes.

Purpose: FOUND-05, and the runner that plan 01-06's two new tables ride on.
Output: one runner, one baseline, one `withTx`, one test that proves an old
database migrates forward.
</objective>

Make a failed migration safe and a migrated database recoverable.

Before the runner applies the first pending migration, and only when the database file already exists and the current `user_version` is below `LATEST_VERSION`, write a snapshot beside it named for the version being left behind — for example `derive.db.bak-v0`. Take the snapshot with SQLite's own single-file copy (`VACUUM INTO`) rather than a filesystem copy of the `.db` file: the database runs in WAL mode, so a raw copy can miss committed pages that are still in the write-ahead log. A fresh database is never snapshotted, because there is nothing to lose. If a snapshot with that name already exists, leave it alone and do not overwrite it — the older snapshot is the one closer to the learner's last known-good state.

Wrap each migration's apply in a try/catch that rolls the transaction back, logs one `[migrate]`-tagged line naming the migration's number and name and the underlying message narrowed with the project's `e instanceof Error ? e.message : String(e)` idiom, and rethrows a lowercase sentence the operator can read as-is, naming the migration and pointing at the snapshot file. Because `server/src/db.ts` runs the runner at import time, the rethrow means the server refuses to start rather than serving on a schema nobody can name — which is the correct failure for a local-first app holding the learner's only record.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| on-disk database -> process | `~/.derive/derive.db` is the learner's only record; the runner rewrites its schema at startup |
| migration list -> SQL execution | `PRAGMA user_version` is set by string interpolation because SQLite forbids a bound parameter there |
| snapshot file -> filesystem | the backup is written beside the database in the data directory |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Tampering | `PRAGMA user_version` interpolation | high | mitigate | the interpolated value comes only from a migration record's `version` field and is validated as a non-negative integer before use; no request data, environment value or file content ever reaches that statement |
| T-05-02 | Denial of service | a half-applied migration | high | mitigate | each migration applies inside a transaction that also carries the version bump, and a failure rolls back, logs `[migrate]` and rethrows so the server refuses to start rather than serving on an unknown schema |
| T-05-03 | Tampering | orphan rows from a crashed delete | medium | mitigate | `withTx` around `deleteLesson`, `replaceGraph` and `deleteLearner` |
| T-05-04 | Information disclosure | the snapshot file | medium | mitigate | the snapshot is written inside `DATA_DIR`, which already holds the database itself, and inherits the same directory; no snapshot is written anywhere else and no path is taken from user input. Plan 01-07 sets the data directory's file mode |
| T-05-05 | Denial of service | unbounded snapshot growth | low | accept | one snapshot per version left behind, never overwritten, and the version count grows with releases, not with use |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | this plan adds no dependency; the runner uses only `node:sqlite`, already a built-in. If execution finds it needs a package, stop and raise it rather than installing |
</threat_model>
