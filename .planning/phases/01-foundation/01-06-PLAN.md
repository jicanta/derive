<objective>
Record what every turn actually cost, honestly, and give later phases something
to hang resume state on.

Per D-13 the grain is the model request, not the turn: Phase 3's owned loop makes
many requests inside one turn and Phase 4 wants tool rejection rate per provider,
and both need the individual calls. Per D-14 it lives in its own table, never as
an event type, so the browser reducer, the SSE stream and the learner's Obsidian
notes are all untouched. Per D-15 a `turns` table comes with it, which also
repairs a named concern: `busy()` and the boot restart-recovery loop currently
read every event of every lesson, and `GET /api/lessons` calls `busy()` per
lesson.

Per D-16 the honesty rule is the point: a turn run by the Claude Code plugin or
the Codex terminal reports no counts, and it still gets a row — nulls and
`cost_source: 'unknown'` — so Phase 4's page can say "6 lessons on the Claude
Code plugin, tokens not reported" rather than quietly leaving them out.
Estimating tokens from transcript length is explicitly rejected.

Purpose: COST-01, plus the `turns` table Phase 3's resume work points at.
Output: two tables, one sink method, one read path repaired, one test.
</objective>

<task type="checkpoint:decision" gate="blocking-human">
  <decision>Fix the column set and the primary key of the turns and usage tables</decision>
  <context>
    D-13, D-14 and D-15 are already decided and are not being re-asked: usage is
    per model request, in its own table, hanging off a new `turns` table. What is
    not yet decided is the exact shape, and that shape is a one-way door. D-15
    records that Phase 3's roadmap already plans a `turn_messages` table for
    resume that needs this to point at, so `turns.id` becomes a key another
    phase's data references. D-13 records that changing the grain later requires
    a migration of accumulated usage history that cannot reconstruct per-request
    detail from turn totals. Both mean: get the columns right now, or migrate a
    learner's real history later.

    The proposed shape, which is option `as-proposed` below:
    `turns(id TEXT PRIMARY KEY, lesson_id, learner_id, driver, model, started_at,
    ended_at, status)` with status one of running / ok / interrupted / error, and
    `usage(id INTEGER PRIMARY KEY AUTOINCREMENT, turn_id, lesson_id, learner_id,
    driver, model, input_tokens, output_tokens, cache_read_tokens,
    cache_write_tokens, reasoning_tokens, cost_source, cost_usd, ts)` with
    cost_source one of provider / table / subscription / unknown, every token
    column nullable, and indexes on turn_id, on (learner_id, ts) and on lesson_id.
  </context>
  <options>
    <option id="as-proposed">
      <name>Take the proposed shape above</name>
      <pros>Covers every field COST-01 names; a random text turn id is stable across restarts and is what Phase 3 can foreign-key to; usage carries lesson_id, learner_id, driver and model denormalised so Phase 4's page needs no join; nullable token columns make D-16's "not reported" representable without a sentinel value</pros>
      <cons>Denormalised columns can disagree with the turn row if a later phase writes them carelessly; cost_usd on a usage row assumes at most one price per request</cons>
    </option>
    <option id="normalised">
      <name>Keep usage minimal and join to turns for lesson, learner, driver and model</name>
      <pros>No possibility of disagreement between the two tables; narrower rows</pros>
      <cons>Every Phase 4 query becomes a join; the model id at the time of the request is lost when a turn changes model mid-turn, which Phase 3's owned loop with a retry on a different model can do — and COST-01 asks specifically for the model id at that time</cons>
    </option>
    <option id="plus-request-id">
      <name>The proposed shape plus a provider request id and a raw provider-usage JSON column</name>
      <pros>Keeps whatever a provider reported that the fixed columns do not model, which is useful when a gateway reports something unusual; a request id makes retries and duplicates identifiable</pros>
      <cons>A JSON blob invites schema-by-accumulation and is the kind of column that never gets cleaned up; two more columns to migrate if they turn out unused</cons>
    </option>
  </options>
  <resume-signal>Select: as-proposed, normalised, or plus-request-id — or describe the column set you want</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| provider response -> usage table | token counts and cost figures reported by a provider are written to the learner's database |
| usage table -> any egress | usage is accounting about the learner; the project's promise is that nothing leaves the machine |
| turns table -> later phases | Phase 3 builds resume state on `turns.id` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Information disclosure | usage data leaving the machine | high | mitigate | usage is written only through `recordUsage` into the local SQLite file; it is deliberately not an event (D-14), so it cannot reach the SSE stream, the Obsidian mirror or the export path, and no network call in this plan reads it |
| T-06-02 | Tampering | a provider over-reporting or under-reporting counts | medium | accept | the provider's own figure is what COST-01 asks to store; Derive records what was reported and labels the source, and `cost_source` is what lets a reader judge it |
| T-06-03 | Repudiation | a turn with no usage row | medium | mitigate | D-16's completeness rule, enforced in the sink's end guard and in the external `end` action, and asserted by `server/test/usage.test.ts` for both the silent-driver and the terminal cases |
| T-06-04 | Tampering | fabricated token counts | high | mitigate | estimation from transcript length or any proxy is prohibited; an unreported count is null with `cost_source` `unknown`, which is checkable in the data rather than being a convention |
| T-06-05 | Denial of service | the backfill pass over the event log | low | mitigate | it runs once, inside migration 2's transaction, and replaces a per-request scan of the same data; a failure rolls back under the plan 01-05 runner |
| T-06-06 | Information disclosure | a model id or cost figure in an error message | low | mitigate | the sink writes usage and does not surface it; error paths are covered by the redaction chokepoint in plan 01-08 |
| T-06-SC | Tampering | npm/pip/cargo installs | high | mitigate | this plan adds no dependency; manifests and `pnpm-lock.yaml` are untouched. If execution finds it needs a package, stop and raise it rather than installing |
</threat_model>
