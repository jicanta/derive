<objective>
Make the front door actually a door.

`/api/*` carries the whole authentication boundary and every control on it is
correct — the 0600 file, the constant-time compare, the Origin allowlist, the
Host check. All of them guard a value that `curl http://127.0.0.1:PORT/` with no
headers at all returns in full, because the token is injected into the
`index.html` that three unguarded routes serve. The verifier read it off `/`,
sent it to `/api/lessons`, and got 200. The same request with `Host: evil.com`
and `Origin: http://evil.com` returns it too.

This plan closes that and the second half of the same defect surface: the Host
allowlist is built from the literal `DERIVE_HOST` string rather than from the
addresses the server answers on, so the documented `DERIVE_HOST=0.0.0.0` refuses
the LAN requests it promises and admits a forged `Host: 127.0.0.1`.

The mechanism supersedes D-09's injection step while strengthening D-09's
intent. D-09 said the app is handed the token inside the document it is served
as, and that no endpoint ever hands the token out. After this plan the app is
handed a *derived* credential inside that document's headers — an HttpOnly,
SameSite=Strict cookie whose value is `HMAC-SHA256(token, "derive browser
session v1")` — and the install token itself never leaves the process at all.
Nothing a hostile page can call, nothing a hostile page can read, and nothing
scrapeable in the markup. D-12 is honoured literally: on a widened bind the
token is still mandatory, presented once, before a browser on another device
gets a cookie.

Purpose: Success Criterion 5's authentication half, which is the one that failed.
Output: one shared Host/Origin guard on every route, a derived browser
credential that is not the token, a Host check bound to the address the
connection landed on, and a test suite whose doc comment is true.
</objective>
