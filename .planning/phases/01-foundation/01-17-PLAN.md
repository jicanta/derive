## The fix shape, decided here, with the reasoning

Three shapes were considered. The reasoning belongs in the plan because a later
reader will otherwise re-derive it.

**Rejected — stop shelling out to git for the listing.** `gitListFiles` exists
so the import honours `.gitignore`. The `walk()` fallback has only a static
`SKIP_DIRS` list, so dropping git means pulling build output, generated files
and vendored trees into the tutor's context on every project that ignores them.
That is a real product regression traded for a security fix that has a cheaper
form.

**Rejected as sufficient on its own — neutralise the environment only.**
`GIT_CONFIG_NOSYSTEM` and the `GIT_CONFIG_GLOBAL` family suppress the *system*
and the *learner's own* config. Neither touches the target repository's
`.git/config`, because that is where a repository's identity lives and git has
no switch to ignore it. An environment-only fix leaves the reproduced vector
open.

**Chosen — pin the knobs on the argv, exactly as the clone argv was pinned.**
Command-line `-c key=value` has the highest precedence in git's config
resolution: it outranks the repository's own file. That is the only layer that
can neutralise an attacker-controlled `.git/config`, and it is applied before
the process exists, which satisfies the standing prohibition against a
confinement check downstream of the thing it confines.

**Which knobs, and which deliberately not.** `ls-files --others` is the reached
vector through `core.fsmonitor`; `core.hooksPath` and `core.pager` are the other
two documented process-spawning knobs a builtin can reach, and pinning them
costs nothing. `core.sshCommand`, `core.askPass`, `credential.helper`,
`diff.external`, `filter.*.clean`/`smudge`, `uploadpack.packObjectsHook` and
`protocol.*.allow` are **not** reachable from `ls-files`: it opens no transport,
runs no diff, filters no content and serves no pack. They are already handled
where they are reachable — the clone argv `01-13` pinned. `alias.*` cannot
shadow a builtin subcommand. `include.path` and `includeIf` can pull in another
config file, but anything that file sets is still outranked by the `-c` values
on the argv. `safe.directory` is a protection rather than a hole; with the
system config suppressed a repository owned by another user may make `ls-files`
fail, which the existing `catch` turns into the `walk()` fallback — a failure in
the safe direction.

Pinning the unreachable ones anyway would leave this file reading as if it
handled cases it cannot reach, which is the same complaint IN-01 and IN-02 make
about it two tasks down. So the unreachable set is named in a comment instead,
with the reason.
