## Schema gate

This project has no ORM and no schema files; `server/src/db.ts` opens
`node:sqlite` and `server/src/migrations.ts` is a hand-written numbered runner
on `PRAGMA user_version`. No schema-push task applies.

What this plan changes about that runner, stated up front because it is a real
decision with a one-way-door quality:

- **It adds a new migration, number 4, named `usage-backfill`.** `LATEST_VERSION`
  becomes 4.
- **It is not a correction to migration 3.** Databases already on `user_version`
  3 exist — the verifier made one, and so did every run of this phase's own
  suite. A corrected migration 3 never re-runs on them, so the repair would
  reach exactly the databases that did not need it.
- **Migration 4 writes rows, not schema.** It adds no table, no column and no
  index, so the "a migrated database lands on exactly the schema a fresh one
  gets" case in `server/test/migrations.test.ts` is unaffected by construction.
- **An install already at `user_version` 3 cannot be un-migrated.** That is why
  Task 1 is a decision checkpoint rather than an assumption. `runMigrations`
  writes `derive.db.bak-v3` through `VACUUM INTO` before applying, so the
  learner keeps a copy of the file as it was — but the forward step itself is
  one-way.

### If Task 1 answered `migration-4`

Write `backfillUsage(db)` as a module-private function beside `backfillTurns`, with a `/** … */` prose doc block in the same register: why it exists (migration 3 created the table and filled nothing for the turns migration 2 had just invented, so `server/src/db.ts`'s stated invariant was false on every upgraded install), what it refuses to do (estimate any figure from the event log — D-16), and why it deliberately skips turns still marked `running` (those are reached by `closeOpenTurns` → `closeUsage` at the next boot, which would otherwise give them a second row).

Its body is one `INSERT … SELECT` over the `turns` table, or the equivalent prepared insert driven by a select — whichever reads better in this file's style. It must:

- select every row from `turns` whose `status` is not `'running'` and whose `id` does not appear in `usage.turn_id`;
- insert one `usage` row per selected turn carrying `turn_id`, `lesson_id`, `learner_id` and `driver` copied from the turn; `model` null; `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens` and `reasoning_tokens` all null; `cost_source` the literal `'unknown'`; `cost_usd` null; and `ts` set to `COALESCE(ended_at, started_at)` from the turn rather than to the current time, so the usage page's `ts` ordering places a historical row where the turn actually happened. Say that last choice in a one-sentence `//` comment — it is the kind of thing a later reader would otherwise 'fix'.
- write nothing when there are no such turns, and write nothing on a second run, which the `NOT IN` / `NOT EXISTS` clause gives for free.

The whole `up` runs inside the transaction `runMigrations` already wraps each migration in, so no extra transaction handling belongs here.
