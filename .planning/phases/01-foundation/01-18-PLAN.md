find that the usage page's arithmetic works on my database too, **so that** the
honest accounting the product promises is not a property of fresh installs only.

Migration 2 backfills one `turns` row per `turn_start` in the event log.
Migration 3 creates the `usage` table and backfills nothing for them. The boot
sweep only reaches rows still marked `running`, so a backfilled turn comes back
`status 'ok', usage_rows 0` and stays that way forever. The verifier reproduced
this with the real pre-phase code — a database built by `server/src/db.ts` at
commit `b8f255c`, opened with HEAD, migrated 0 → 3, every row kept,
`derive.db.bak-v0` written — and it came back `turns: 1, usage: 0`.

`server/src/db.ts:640` says, without qualification, that every turn gets a
usage row whichever driver ran it, and that turn counts reconcile across every
view. On every upgraded install — which is every existing learner — that is
false. **D-16** is what the sentence is quoting: a usage row is written for
every turn regardless of driver, with null token fields and `cost_source
'unknown'` when nothing was reported, so Phase 4's usage page can honestly say
"six lessons on the Claude Code plugin — tokens not reported" instead of
silently omitting them. The standing prohibition three earlier plans carry says
pick one repair or the other, not neither.

The second half is its sibling. `server/src/index.ts:1000-1002` calls
`finishTurn` and then `closeUsage` as two statements, where `closeOpenTurns`
wraps exactly that pair in one `withTx`; `server/src/driver.ts:113-115` does the
same. A crash between the two leaves a turn marked ended with no usage row and
no sweep that can ever reach it, because the sweep filters `WHERE status =
'running'`. The verifier recorded that key link as PARTIAL.

## Schema gate

This project has no ORM and no schema files; `server/src/db.ts` opens
`node:sqlite` and `server/src/migrations.ts` is a hand-written numbered runner
on `PRAGMA user_version`. No schema-push task applies.

What this plan changes about that runner, stated up front because it is a real
decision with a one-way-door quality:

- **It adds a new migration, number 4, named `usage-backfill`.** `LATEST_VERSION`
  becomes 4.
- **It is not a correction to migration 3.** Databases already on `user_version`
  3 exist — the verifier made one, and so did every run of this phase's own
  suite. A corrected migration 3 never re-runs on them, so the repair would
  reach exactly the databases that did not need it.
- **Migration 4 writes rows, not schema.** It adds no table, no column and no
  index, so the "a migrated database lands on exactly the schema a fresh one
  gets" case in `server/test/migrations.test.ts` is unaffected by construction.
- **An install already at `user_version` 3 cannot be un-migrated.** That is why
  Task 1 is a decision checkpoint rather than an assumption. `runMigrations`
  writes `derive.db.bak-v3` through `VACUUM INTO` before applying, so the
  learner keeps a copy of the file as it was — but the forward step itself is
  one-way.
