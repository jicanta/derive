<objective>
**As a learner** who has just been told that deleting one file signs every
browser out, **I want to** have that actually happen on the server that is
running in front of me, **so that** when I believe a credential has leaked the
thing the product told me to do is the thing that works.

The fourth verification reproduced it end to end. A browser signed in with
`GET /?token=<t>` and held `derive_session=<hmac>; Max-Age=2592000`. Deleting
`~/.derive/token` on the running server left the cookie at 200, the old
`x-derive-token` header at 200 and `GET /` at 200. Nothing was revoked.

The mechanism is plain: the install token is read exactly once, at module
evaluation, the session value is derived from it once, and the two comparison
buffers beside them are frozen module state. Both credential middlewares
compare against those buffers. Nothing re-reads the file, so deleting or
rotating it changes nothing until the process restarts — and because the
boot-time creation then makes a *different* token, the learner gets no signal
that the revocation they performed was a no-op.

Four learner-facing places state the opposite, as the stated justification for
a thirty-day persistent cookie. And the case named for this control passes by
starting a *second* server with its own data directory and asserting the first
refuses the second's cookie. That is install isolation, not revocation, and it
is exactly how a control that does not work shipped green.

Purpose: **FOUND-06** — the per-install token and the sentences about it —
closed on the one clause that is false.
Output: one live read of the token file behind a short cache, both credential
middlewares and the cookie mint reading it, five sentences that describe it,
and a case that deletes the token file of a running server and asserts the
refusals.
</objective>

## The decision taken before building, and the reasoning

The verification offered two branches and required the choice to be recorded
before a line was written, the way `01-18` recorded its ledger-shape branch.
**The decision is branch (a): make revocation real.** It is recorded here and
is not re-opened by execution.

Branch (b) — correcting all four sentences to say "delete the token file **and
restart derive**" — was available and was rejected. The sentence that would
result is the one the learner needs in the worst moment the product has: a
widened `DERIVE_HOST` bind, plaintext over a LAN, a credential the learner
believes has leaked. Telling them to restart a server that is in the middle of
their lesson, on the strength of a file they cannot read, is a worse product
than a one-second read. The fix is a cached `readFileSync`, which is smaller
than the documentation change it replaces.

**The window is one second, and the sentences say so.** Revocation behind a
cache is not instantaneous, and the standing prohibition of this phase forbids
describing it as if it were. Every sentence that asserts revocation names the
window. A learner reading "within a second, without restarting derive" is being
told exactly what happens.

**A deletion fails closed and creates nothing.** The boot-time creation stays
where it is — it runs once, at start, and is what makes a first run work. The
live path never creates: an absent, empty or unreadable file means no
credential authenticates, full stop. Falling back to the boot snapshot would
reproduce the bug, and creating a fresh token on the credential path would
reproduce the worse half of it, where the learner's revocation silently
re-opens the door under a value they were never shown.

**The live value is promoted, not added alongside.** See
`<assumption_delta_decision>` below. The boot-derived comparison buffers are
deleted rather than left unconsulted, because two sources of truth for one
credential drift apart and the one that drifts is the one the learner was told
to rely on.

<assumption_delta_decision>
**Signal:** `chosen`-family — a value that was a constant read once at module
evaluation becomes a live read behind a cache.

**The noun that is now primary:** the **live install token on disk**, and the
session value derived from it. The value this process read at boot is no longer
a credential; it survives only as the string printed in the startup link.

**Decision: `promote`.**

**Rationale:** `add-alongside` is the defect. A boot snapshot kept next to a
live read gives one credential two sources of truth, and the whole gap is what
happens when a check consults the stale one. Promotion is therefore structural
rather than stylistic: the boot-derived comparison buffers and the helper that
compared against them are **deleted** from the route file, so there is nothing
left for a future edit to consult by accident. A reviewer can confirm the
promotion by the absence of a comparable snapshot, not by reading intent.

**What would force a later revisit (not a promote — this is already promoted):**
if per-request `readFileSync` cost ever shows up on a profile, the answer is a
watcher on the token file rather than a longer cache or a restored snapshot —
and if the window changes, the three sentences that name it change in the same
commit.

**Suggested contract test (not required to gate the plan):** a case that
encodes the generalised intent — *no credential check consults a value the
token file no longer holds* — so a future change that reintroduces a boot
snapshot goes red rather than merely un-reviewed. Task 2 carries it as a
source-shaped regression gate over the route file's credential comparisons.
</assumption_delta_decision>
