## The decision taken before building

The verification offered two branches: add the pins, or rewrite the sentence to
say the knobs are pinned on neither path. **The decision is to add the pins**,
and it is recorded here rather than re-opened by execution. They cost nothing —
five `-c` flags and one environment variable on a call that already carries
three of each kind — and a clone that opens a transport is the path on which the
transport and credential knobs are genuinely reachable, so pinning them there is
where they belong.

**And then the sentence still has to change**, in the other direction. Three of
the six knobs the comment names are *not* in the decided pin list:
check-in content filters, an external diff driver and a pack-objects hook. After
this plan they are pinned on neither argv. A sentence that names six and pins
five is the same defect as one that names six and pins one; the fix is only
complete when the comment says which knobs ride on which argv and names the
three that ride on neither, with the reason. Leaving that half undone would be
this gap reopened one knob narrower.

**Size it accordingly.** No exploit follows from this today. This is a
correctness-of-the-security-comment fix with a regression gate attached, not an
incident response, and it should read like one.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a cloned repository's own `.git/config` → the git process Derive spawns | the clone destination is fresh and written by git, so a hostile remote cannot set config there — which is why this is a warning and not an incident |
| the machine's system git config → the git process Derive spawns | `/etc/gitconfig` is not attacker-controlled data, but the listing path already drops it and the clone path did not, so the two paths disagreed about the same class of input |
| the learner's global git config → the clone | a credential helper defined there is host-scoped and would only ever be consulted for the host the learner is cloning from; the argv pin removes the question rather than reasoning about it |
| a security comment → the next maintainer | a comment naming a mitigation is read as coverage; the next person to make a knob reachable acts on what it says |
