<objective>
**As the owner** of a phase that has failed five verifications in a row, **I
want** this round to make the authenticated surface *smaller* rather than
larger, **so that** the criterion being verified stops quantifying over an area
that grows every time it is checked.

The fifth verification's two findings are both on credential paths that earlier
gap rounds added. The one-time ticket (01-18) is never spent when the browser
holds the cookie (01-19), so it survives its own use on the browser opener's
argv — the exact exposure it was written to close. The one-second revocation
cache (01-20) treats every backwards clock step as fresh, so a deleted token
keeps authenticating for the length of the step.

Both are real. Neither is worth a sixth additive round. The ticket exists only
because the MCP server hands a URL to a browser opener through a process
command line — and `mcp.ts:213` already implements, and already documents as
acceptable, the path where there is no ticket to hand: open the bare URL and
let the 401 body tell the learner to open the link the server printed. Deleting
the ticket closes the argv exposure *by construction* rather than by a
sixty-second lifetime, removes the branch that the cookie short-circuit
bypasses, and removes two claims that have to stay true.

What remains is a browser that signs in with `?token=` and holds a derived
cookie, and a machine client that sends `x-derive-token`. Two paths, both
already driven green.

Purpose: **FOUND-06** — closed by making the surface small enough that
Criterion 5's universal claim has a finite, enumerable domain.
Output: one deleted module, one deleted route, one reordered middleware, one
comparison fixed, and the cases that hold each.
</objective>

The one first-run cost is real and is accepted deliberately: a browser that has

token file, and the server's startup line already prints the full `?token=`
link. It is one extra step, once per browser, and it buys the deletion of a
credential that travels on a world-readable command line.

  <action>
Move the URL-credential check ahead of the cookie short-circuit, so a
credential that travels in an address bar is always spent and always dropped.

Today `matchesSession(cookie)` returns before either handoff is reached, which
is why a `?token=` open by an already-signed-in browser leaves the token in the
URL and never refreshes the cookie — making the four sentences listed in
`read_first` false for the ordinary case.

Restructure the credential step so the query parameter is considered first:
when `?token=` is present at all, decide on it and return — a match issues the
session and redirects to the bare path, a non-match is a 401. Only when there is
no `?token=` in the URL do the cookie and then the `x-derive-token` header get
their turn, and both of those pass through with `next()` rather than
redirecting. Treat the header as a pass-through rather than a handoff: there is
nothing in a header to strip from a URL, and redirecting it is what would let a
header-carrying client loop.

Update the middleware docstring's closing sentence — the one that currently
reads "the cookie, then the install token, then the one-time ticket" — to name
the order the code now has, and say in one clause why a URL credential goes
first: it has to be spent and dropped even for a browser that is already signed
in. Delete the sentence about a browser presenting the token "once"; it presents
it whenever it opens the link, which is the point. Add no other prose.

Add two cases to `server/test/security.test.ts`, in the describe that holds the
existing handoff cases: one driving a browser that holds a valid cookie through
`GET /?token=<valid>` and asserting a 302, a `Set-Cookie`, and a `Location`
without a query string; one driving a client that repeats `x-derive-token`
against `GET /` twice and asserting 200 both times with no `Set-Cookie` and no
`Location` — the no-loop guarantee.
