**4. The loop — `server/src/drivers/api.ts` (new).** A `/** … */` prose module header explaining that this is Derive's own agent loop: one `streamText` per turn, the history accumulated from `fullStream` rather than asked of the SDK at the end (because `result.responseMessages` rejects after an abort, which is the one moment the history matters most), and tool execution serialised inside `execute` because the SDK runs a step's tool calls with `Promise.all` and Gemini has no provider flag to turn that off.

Export `apiDriver: Driver`. `Driver.name` must be the resolved `ProviderId`, never the literal `api`: `providerOfDriver(driver)` is the identity outside `'claude'`, `lessonView` feeds it straight to the header pill, and `recordUsage` denormalises `turn.driver` onto every usage row, so one driver named `api` would collapse five providers into one label. Implement this by exporting a factory the dispatch calls — `apiDriverFor(provider: ProviderId): Driver` returning `{ name: provider, runTurn }` — and keep `apiDriver` as the `Driver`-shaped export the suite can hand to `setDriverOverride`.

Export `setModelOverride(factory: ModelFactory | null)` / `modelOverride()` with the same posture `driver.ts`'s `setDriverOverride` documents in its doc comment: no route, header, environment variable or config file can set it, and the production path still reads the adapter table. `type ModelFactory = (provider: ProviderId, modelId: string | null) => LanguageModel`. This is how Success Criterion 1's stub model reaches the **real** loop rather than replacing it.

`runTurn(ctx, sink)` does, in order:
  - Resolve the provider from `Driver.name`, read the key with `effectiveKey(provider)` and the base URL with `getSetting(baseUrlKey(provider))`, and build the model through `modelOverride()?.(provider, ctx.model ?? null) ?? adapterFor(provider).model(key, base, ctx.model ?? null)`. The driver must not read `process.env`: `config.ts` is the only module that does.
  - Register the interrupt before the request: create an `AbortController`, and `ctx.onActive({ interrupt: async () => controller.abort() })`.
  - Build the tool set from `toolsFor('agent')`: for each spec, `tool({ description: descriptionFor(spec, 'agent'), inputSchema: jsonSchema(jsonSchemaOf(spec, 'agent')), execute })`. Pass a pre-projected JSON Schema through `jsonSchema(...)`, **never** a zod schema — when `inputSchema` is a zod schema the SDK runs its own conversion and emits draft-07, where this repo's `jsonSchemaOf` emits draft-2020-12, so the bytes on the wire would stop matching `wire-surface.json`. (Plan 03-07 widens this to the per-dialect projection; plan 03-06 moves the surface to `'api'` when `fetch_page` arrives.)
  - Serialise tool execution: a module-level `const chains = new Map<string, Promise<unknown>>()` and a `serialise(lessonId, f)` helper that chains onto the lesson's previous promise and stores `next.catch(() => undefined)` so one failure does not poison the chain. Every tool's `execute` enters it, emits `sink.emitEphemeral('status', { text: TOOL_LABELS[spec.name] ?? \`Using ${spec.name}\` })`, then awaits `actions.runTool(ctx.lessonId, spec.name, input)`. Results are returned in arrival order. This is D-08's backstop and on Gemini it will be the only mechanism.
  - Call `streamText({ model, instructions: [{ role: 'system', content: ctx.instructions }], messages, tools, toolOrder: [...toolsFor('agent').map((s) => s.name)], stopWhen: isStepCount(400), maxRetries: 0, abortSignal: controller.signal, providerOptions })`. `instructions` is the array form from the start because that is the shape D-06's stable/volatile cache split needs in plan 03-08, and because `allowSystemInMessages` defaults to `false`, so a system message inside `messages` would be refused. `messages` is `[{ role: 'user', content: ctx.prompt }]` in this task; plan 03-04 seeds it from the persisted history. Do **not** set `streamRetries`. Write the 400 and its reasoning as a one-sentence `//` comment beside it, in the voice of `schedule.ts`'s floor comment: 400 mirrors today's `maxTurns: 400` so no existing lesson behaves differently, the unit is model calls rather than agent turns, and the cap is a runaway guard rather than a teaching limit — hitting it ends the turn through the normal `turn_end` with a continuable status, the same shape as a Stop.
  - Consume `for await (const part of r.fullStream)` and map parts onto sink calls, copying `agent.ts`'s growing-block machinery verbatim (`blockId`/`blockSeq`/`blockText`/`lastCheckpoint`, a `flushBlock()` closure, and the ~1500 ms `sink.checkpoint` cadence): `text-start` → `flushBlock()` then `blockSeq = sink.emit('assistant', { id, text: '', partial: true }).seq`; `text-delta` → append, `sink.emitEphemeral('delta', { id, text: part.text })`, checkpoint on cadence; `text-end` → `flushBlock()`; `reasoning-start` → `sink.emitEphemeral('status', { text: 'Thinking' })` and nothing else, and discard `reasoning-delta`/`reasoning-end` entirely; `tool-call` → accumulate an assistant `ToolCallPart` into the history array; `tool-result` / `tool-error` → accumulate a `ToolModelMessage`; `start-step` → for each `part.warnings` entry of type `unsupported`, `sink.emitEphemeral('status', { text: \`This model does not support ${w.feature}\` })`; `finish-step` → one `sink.usage(row)`; `abort` → `flushBlock()` and break.
  - The usage row maps `model` from `part.response.modelId` falling back to the asked model, `input_tokens` from `part.usage.inputTokenDetails.noCacheTokens`, `output_tokens` from `part.usage.outputTokens`, `cache_read_tokens` / `cache_write_tokens` from `part.usage.inputTokenDetails.cacheReadTokens` / `cacheWriteTokens`, `reasoning_tokens` from `part.usage.outputTokenDetails.reasoningTokens`, and `cost_source: 'unknown'` with `cost_usd: null` in this task (plan 03-08 supplies the figure). Reuse `agent.ts`'s `reported(v)` discipline so a count the provider did not give stays `null`, never `0`. Mapping `input_tokens` from `part.usage.inputTokens` is the one mistake to avoid: that total already includes cache reads and writes, and this repo's `input_tokens` column means the uncached part, so a cached lesson would read roughly twice the input tokens it should.
  - End the turn with `agent.ts`'s exact discipline: `if (ctx.isStopping()) sink.endTurn({ ok: true, interrupted: true })` else `sink.endTurn({ ok: true, verified })` on a clean finish; `catch (err) { flushBlock(); sink.endTurn({ ok: false, error: safeMessage(err) }); }`; `finally { flushBlock(); sink.endTurn({ ok: true, interrupted: true }); }`. `sink.endTurn` is idempotent, which is what makes the `finally` safe. `verified` is a counter this task initialises to 0 and plan 03-06 increments on the search and fetch tools.
