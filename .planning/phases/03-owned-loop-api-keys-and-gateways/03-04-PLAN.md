<objective>
**As a** learner who pressed Stop, or whose machine restarted mid-lesson, **I want to** send the next message and have the lesson carry on, **so that** an interruption costs me a turn rather than a lesson.

This refines the tracer's slice with the half of PROV-08 the tracer deliberately left as a functionality gap: the history the loop already accumulates in memory becomes persisted state, orphaned tool calls get a synthesized result so the history stays acceptable to a provider, and a replay returns the result it recorded instead of grading a quiz twice. It also fixes WR-01 in the same pass, because this is the phase that takes teaching providers from two to seven and turns a latent bug into one learners will hit.

Purpose: make PROV-08's resume clause literally true rather than usually true.
Output: migrations 6 and 7, the `turn_messages` accessors and the executed-call record, the per-provider `LearnerPrefs.model`, the loop's load/save/patch/replay path, and the suites that cover all of it.
</objective>

  <action>
Make the history the loop already accumulates into persisted, resumable state.

**1. Load before the request.** At the top of `runTurn`, `const prior = loadTurnMessages(ctx.lessonId, provider)` and start the request's `messages` as `[...prior, { role: 'user', content: ctx.prompt }]`. `loadTurnMessages` already returns an empty array when the stored driver differs, so D-04's drop-on-provider-change needs no branch here. In `server/src/agent.ts`, extend the existing session-id clear to call `clearTurnMessages(lessonId)` on the same condition and in the same place, and extend that comment's second sentence to say that the persisted messages go with the session id for the same reason: a provider's reasoning signatures and thought signatures are not portable, so carrying a history across a switch would replay one vendor's opaque blocks into another that rejects them.

**2. Accumulate and save.** Keep accumulating from `fullStream` — never from `result.responseMessages`, which rejects after an abort, which is the one moment the history matters most; put that reasoning in a single-line `//` comment beside the accumulation so nobody simplifies it later. Write that comment as a `//` line rather than a block comment: the gate below strips `//` text before grepping, so a `//` explanation is free while the identifier appearing in real code is the regression it catches. Store only `assistant`, `tool` and `user` messages: the system prompt is rebuilt from `method/` every turn and rides `instructions` as a separate field, so a persisted system message would be stale method text. Persist the parts **verbatim**, including `providerOptions` — Anthropic's compaction signature and Google's per-block signature live there and are round-tripped on the next turn, so nothing may filter or rewrite a part. Call `saveTurnMessages(ctx.lessonId, provider, accumulated)` at the end of each `finish-step` and again in the `finally`, so a crash between steps loses at most the step in flight.

**3. Replay by call id.** Inside each tool's `execute`, within the mutex and before anything else, `const recorded = recordedToolResult(turnId, toolCallId); if (recorded) return recorded.output;`. After the action returns, `recordToolResult(turnId, ctx.lessonId, toolCallId, spec.name, out)` in the same step as appending the `tool-result` part to the accumulated history, so the guard and the history can never disagree. The driver needs the turn id for this; take it from the sink's turn rather than inventing a second identifier — thread it through `TurnContext` as a new `turnId: string` field in `server/src/driver.ts` if it is not already available, and set it in `agent.ts` where `startTurn` returns it. Write the reason beside the guard in one sentence: this is the only version under which resuming cannot re-grade a quiz, and a re-graded quiz moves an FSRS row the learner already earned.

**4. Patch orphans on abort.** Write `patchOrphans(accumulated)`: walk the accumulated history for assistant `ToolCallPart`s whose `toolCallId` has no matching `ToolResultPart`, and append one `ToolModelMessage` whose content is a synthesized `ToolResultPart` per unanswered id, with `output: { type: 'error-text', value: 'The learner stopped the turn before this tool ran.' }`. `error-text` is the purpose-built `ToolResultOutput` shape and every provider adapter maps it to its own error-result encoding. Call `patchOrphans` on the `abort` part and in the `catch`, before the save, so the persisted history is always one a provider will accept on the next turn. Then `flushBlock()` and let the existing end-of-turn pair run: `ctx.isStopping()` takes the `{ ok: true, interrupted: true }` branch, which is what keeps a Stop distinct from a failure and the lesson resumable.

**5. The step cap ends the same way.** When the loop finishes because `isStepCount(400)` was met rather than because the model stopped, end through the normal `turn_end` with a continuable status — the same `{ ok: true, interrupted: true }` shape as a Stop, never an error card and never a lost lesson. Detect it by comparing the final step count against the cap and write the reason in a one-sentence comment: the cap is a runaway guard, not a teaching limit.
  </action>
