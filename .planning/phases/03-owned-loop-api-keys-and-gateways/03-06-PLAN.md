<objective>
**As a** learner on any provider, **I want to** be taught by a tutor that can check a fact before teaching it and read a source I point it at, **so that** a wrong root never corrupts every node built on top of it — and when no search is available, **I want to** be told the tutor is unsure rather than be told something confidently wrong.

This adds a new slice end to end: the fallback search service, the one fetch tool on the existing guarded fetcher, the `api` tool surface that keeps both off the plugin's wire, the third `{{WEB_TOOLS}}` rendering with its no-search variant, and the settings routes the card in plan 03-09 will drive.

Purpose: the method requires the tutor to verify a fact before teaching it, and a learner on OpenRouter has no way to do that without this.
Output: `server/src/search.ts`, the `fetch_page` tool and the `api` surface, the three `{{WEB_TOOLS}}` renderings, the native-search adapters, the web-search settings routes, and the suites.
</objective>

Build the fallback search as one service with two backends, and the two routes that configure it. The card that drives these routes is plan 03-09; this task delivers the server side and its suite.

**1. `server/src/config.ts`.** Add `export const SEARCH_KEY_ID = 'search:tavily';` with a one-line doc comment naming it as the id the Tavily key is stored under in `secrets.json`, so the key rides `keys.ts` rather than a new path. Add `TAVILY_API_KEY` to the `EnvKeyName` union and to `ENV_KEYS`, so a learner who prefers an environment variable gets one and `lockedBy` can name it — `config.ts` is the only module that may read `process.env`, which is why the variable is declared here and nowhere else.

**2. `server/src/search.ts` (new).** A `/** … */` prose module header explaining why the module exists in one paragraph: three of the five providers search with their own tool, and a learner on OpenRouter or a base-URL endpoint has no way to check a fact without this; the method requires the tutor to verify before teaching, so a tutor with no way to check is a tutor that asserts.

Export `type SearchProvider = 'provider' | 'tavily' | 'searxng'` and `SEARCH_PROVIDERS` as the `as const` runtime list that doubles as the type, following the `RESOURCE_KINDS` idiom. Export the two setting keys as constants (`SEARCH_SETTING = 'search_provider'`, `SEARCH_BASE_URL = 'search_base_url'`) so the routes and the service cannot disagree about where the choice lives. Export `searchProvider(): SearchProvider` reading `getSetting(SEARCH_SETTING)` and defaulting to `'provider'`.

Export `type SearchHit = { title: string; url: string; snippet: string }` and `searchWeb(query: string, limit = 5): Promise<SearchHit[]>`:
  - Refuse an empty or whitespace-only query with `throw new Error('a search needs a query')` before any request. Clamp `limit` to a small bound.
  - Dispatch on `searchProvider()`. `'tavily'` calls `tavilySearch`, `'searxng'` calls `searxngSearch`, and `'provider'` throws `there is no web search configured for this provider` — the loop never calls `searchWeb` in that case, so this throw is the guard against a future caller rather than a learner-facing path.
  - `tavilySearch`: `POST https://api.tavily.com/search` with `Authorization: Bearer <key>`, `content-type: application/json` and the body `{ query }`. The key comes from `effectiveKey(SEARCH_KEY_ID)` so the environment variable outranks the file exactly as it does for a provider key. Map `results[]` to `SearchHit` using `title`, `url` and `content`, preserving the provider's order with no re-ranking and no deduplication. A missing key throws `add a tavily key in settings to turn on web search`.
  - `searxngSearch`: `GET <base>/search?q=<query>&format=json` against the learner's stored base URL, with no authentication. When the base URL is absent, throw `add your searxng address in settings to turn on web search`. Map `results[]` to `SearchHit` using `title`, `url` and `content`.
  - Both use `redirect: 'manual'` and `AbortSignal.timeout(timeoutFor(url))`, where `timeoutFor` is `probe.ts`'s posture: `isLocalUrl(url) ? LOCAL_MS : REMOTE_MS`. Import `isLocalUrl`, `LOCAL_MS`, `REMOTE_MS`, `providerSentence` and `hintFor` from `probe.ts` rather than writing a second error vocabulary or a second timeout rule.
  - **Do not** call `assertPublicHost` on the configured SearXNG base URL. A learner's SearXNG is very often on `localhost` or a `.local` name, and `assertPublicHost` throws for exactly those; the guard exists to stop Derive fetching private addresses on a *model's* instruction, not to stop a learner naming their own server. Write that as a one-sentence `//` comment at the call site that would otherwise be tempting — a `//` line rather than a block comment, because the gate below strips `//` text before grepping, so the explanation is free while a real call to the guard in this module is the regression it catches.
  - The SearXNG JSON-disabled case gets its own sentence: when the response is not OK, or is OK but does not parse as JSON carrying a `results` array, throw `your searxng instance did not answer with json; enable the json format under search: in its settings.yml`. It is the single most likely SearXNG failure, and collapsing it into a generic reach error would send the learner looking in the wrong place. A non-OK response from either backend otherwise carries `providerSentence(res.status, text)`.

Export `testSearch(): Promise<TestResult>` in the exact shape `probe.ts` `testConnection` already returns — `{ ok: true, models: number | null, ms } | { ok: false, error, hint?, ms }` — reusing that type so the browser's existing `resultText` renderer works with no new shape. For a search test, run a fixed one-word query and report the hit count in the `models` field, which is what makes the UI-SPEC's `Connected · {n} results · {ms} ms` line renderable from the existing component. A `'provider'` choice answers `{ ok: true, models: null, ms: 0 }` with nothing tested, because there is nothing of Derive's to test.

  - `POST /api/settings/search/test` — calls `testSearch()` and answers its result. Like the provider test, it never throws for a search failure; the result says.
