<objective>
**As a** learner on a provider with a fussy schema dialect, **I want to** get the same tutor with the same tool contract as everyone else, **so that** my provider's limitations do not quietly become my tutor's limitations.

This refines the loop's tool registration with the per-dialect projection PROV-10 asks for, and closes its server-side half: whatever a provider's dialect had to drop, the server still validates an incoming call against the full schema. The registry is untouched — only the projection adapts.

Purpose: let each provider see a schema it accepts, without letting the weakest dialect set the contract for all of them.
Output: `jsonSchemaOf(spec, surface, dialect)`, the full-schema validator in the loop, the dialect keys in the frozen fixture, and the outright rules checks.
</objective>

  <action>
Widen the projection and add the validator. Do not fork `jsonSchemaOf` and do not touch a single registry row.

**1. The dialect type.** Export `const TOOL_DIALECTS = ['full', 'openai-strict', 'gemini', 'compact'] as const` and `export type ToolDialect = (typeof TOOL_DIALECTS)[number]`, following the `as const` plus `typeof` idiom the repo already uses for runtime lists that double as types. `'full'` is the registry's own projection and the default, so every existing caller keeps working unchanged.

**2. Widen `jsonSchemaOf`.** Change the signature to `jsonSchemaOf(spec: ToolSpec, surface?: ToolSurface, dialect: ToolDialect = 'full')` and keep the body built on zod's own seam rather than a post-hoc object walk where zod can do it: `z.toJSONSchema(z.object(surface ? shapeFor(spec, surface) : spec.shape), opts)` with per-dialect `opts`. Use the `override: (ctx) => void` hook for the per-dialect rewriting — it is documented as "arbitrary custom logic that can be used to modify the generated JSON Schema", needs no new dependency, and keeps the registry untouched exactly as D-28 requires. Keep the one-line doc comment and extend it to name the dialect parameter.

The four dialects:
  - `'full'` — byte-identical to what `jsonSchemaOf(spec, surface)` emits today. This is the assertion the existing fixture already freezes, so it must not move by a byte.
  - `'openai-strict'` — drop `minItems`, `maxItems`, `minimum` and `maximum` wherever they appear (all four are on OpenAI's unsupported list); put **every** property name into `required`; express each originally-optional property as a nullable union — `type: ['string', 'null']` and so on — adding `null` to any `enum` that gains it; keep `additionalProperties: false`, which the registry already emits; and drop `$schema`, which is tidier and which OpenAI's normaliser would preserve as an unknown key. Record in a comment that the cost of this dialect is exactly those four bounds, which `set_plan` (3-12 nodes) and `quiz` (2-3 options) rely on — that is why it is not the default.
  - `'gemini'` — emit only `type`, `properties`, `required`, `description`, `enum` and `items`; drop `$schema`, `additionalProperties`, `minItems`, `maxItems`, `minimum` and `maximum`. Google passes `parametersJsonSchema` through verbatim, so a keyword it rejects returns a 400 from Google rather than a warning, which is why this dialect is subtractive rather than clever. Note in the comment that the exact rejected set is LOW confidence (`03-RESEARCH.md` A3) and that this projection is the safe subset of the keyword inventory the registry actually emits; the real-key confirmation is a human check below. Do not reach for `target: 'openapi-3.0'` as a shortcut — it produces OpenAPI-3.0 nullability (`nullable: true`) rather than JSON Schema unions, and that is a different wire shape than Gemini is being promised.
  - `'compact'` — the same keyword set as `'full'` with every `description` shortened to its first sentence (or a bounded prefix, whichever is shorter). This is the hook Phase 4's local models need; it ships here so PROV-10's "compact for local" is delivered and CI-validated rather than invented later.

On the `io` option: check whether switching from zod's default `io: 'output'` to `io: 'input'` changes any of the 22 tools' `'full'` projections. If it does not, switch it — `'input'` is semantically correct for a tool *input* schema — and record in a one-sentence comment that the switch moved nothing. If it does change a projection, leave it at the default and record why, because moving the frozen fixture for a semantic preference is not a change this phase needs.

**3. The validator — `validateToolInput`.** Export `validateToolInput(spec: ToolSpec, surface: ToolSurface, input: unknown): Record<string, unknown>`: build the **full** zod object for that spec and surface with `shapeFor` and `safeParse` the input, returning the parsed value on success and throwing `new Error(...)` with a lowercase sentence naming the first failing field on failure, in the shape `index.ts`'s route handlers already use (`parsed.error.issues[0]?.message`). This is PROV-10's server-side half: a provider's narrower dialect never narrows what Derive accepts, so a field the strict projection had to flatten into a nullable union is still checked here against the real shape. One line of doc comment saying exactly that, because the reason is the whole point.

**4. `server/src/drivers/adapters.ts` — each row names its dialect.** Add `dialect: ToolDialect` to the `Adapter` type and set it per row: `anthropic` → `'full'` (Anthropic does no schema normalisation of note and has no strict mode); `openai` → `'full'`, **not** `'openai-strict'` — strict mode is opt-in per tool and off by default, and enabling it would cost the bounds the tutor is held to, so the strict projection ships as the thing CI validates and Phase 4's harness can switch on; `gemini` → `'gemini'`; `openrouter` → `'full'` (it fronts many models and normalises nothing of note); `openai-compatible` → `'full'`. Write the OpenAI decision as a one-sentence comment beside the row, because a reviewer will ask why the strict dialect exists and is not used.

**5. `server/src/drivers/api.ts` — project with the dialect, validate with the full schema.** Change the tool build to `inputSchema: jsonSchema(jsonSchemaOf(spec, 'api', adapterFor(provider).dialect))`, still passing a pre-projected schema through `jsonSchema(...)` and never a zod schema. Then, inside each tool's `execute` and inside the existing mutex, call `validateToolInput(spec, 'api', input)` **before** `actions.runTool` and pass the parsed value on. Order matters: the replay guard from plan 03-04 runs first (a recorded result is returned without re-validating a call that already succeeded), then validation, then the action. A validation failure throws, which the SDK surfaces as a tool error the model can correct from — that is the right shape, because a malformed call is the model's mistake to fix rather than a turn to fail.
