## Phase Goal

**As a** learner, **I want to** run Derive free and offline on a local model without the method silently degrading, prove any chosen model runs the method before I invest a session, and see what learning has cost across every provider, **so that** I am taught the Derive way on whatever model I have access to, with nothing lost between providers.

This plan delivers the proof half of the second clause: one node, one graded quiz, pass or fail, before a session is spent.

<objective>
Give Settings an action that proves the chosen model can actually run the method, in about a second, without leaving a trace.

Purpose: a weak local model fails the understanding gate often — the roadmap says to expect it — and finding that out forty minutes into a lesson is the cost this action removes. It proves exactly what PROV-11 claims: the model can call the method's tools and its quiz is gradable. Not that it teaches well.

Output: migration 8 adding the `lessons.scratch` marker; a `scratch` option on `createLesson`, `listLessons` excluding scratch rows, and `sweepScratchLessons` on the boot pass; `driverFor` and `runTurn`'s per-turn provider-and-model option, the seam that lets a turn run on a row that is not the active provider; `testTeaching` in `capability.ts`; a `POST /api/settings/:provider/test-teaching` route; the `test teaching` control on every teachable row with its approved readouts; and the UI-SPEC amendment D-13 requires.
</objective>

## Amendments to locked decisions (recorded with their rationale)

**A-03 — the scope of Test teaching (owner decision, this planning session).** D-13 puts the action on "every teachable provider row", and `04-UI-SPEC.md` placed it on the local rows only. **Test teaching runs on every provider row, including the Claude Code and Codex login rows.** Both login backends implement `Driver.runTurn`, so the same one-node-one-graded-quiz probe works unchanged on them; the owned loop's `adapterFor` throws for both permanently, which is a fact about *that loop* and not about whether the row can teach. A learner on a login row must not be left without a way to run the proof. D-13 already required a UI-SPEC amendment for this action, and that amendment now covers these two rows as well — Task 3 writes it.

**Why this is not the `teaches` trap (04-RESEARCH §Pitfall 10).** `teaches` and "runs through the owned loop" are different predicates, and conflating them is the documented failure here. The control keys on `row.teaches`, and the server dispatches each row to *its own* driver rather than assuming the owned loop — which is precisely what the driver seam exists for.

## Claude's Discretion resolved (CONTEXT.md left these to the planner)

**The scratch lesson's marker.** `04-RESEARCH.md` §Pattern 6 leaves this open and asks for "the narrowest change that `deleteLesson` already cleans up". A sentinel topic is fragile — a learner can type any topic. A new `mode` value widens a union the whole app switches on. Encoding the fact in the lesson **id** would mean parsing meaning out of a primary key, which is the pattern this codebase avoids (`recordUsage` denormalises the driver and the model onto every row rather than deriving them later). So: **a `lessons.scratch` column through migration 8** — explicit, typed, and already cleaned up by `deleteLesson`'s single transaction. `listLessons` excludes scratch rows and a boot-time `sweepScratchLessons` removes any that survived a crash. The server `Lesson` type gains the field; the hand-mirrored `web/src/lib/types.ts` `Lesson` deliberately does **not** — the browser never reads it, and an unread field on a locked UI surface is surface for nothing.

**The scripted probe and its assertions.** One fixed trivial topic, one turn, and a required sequence: set a plan, teach one node, ask one quiz. The probe settles the quiz card itself and lets `actions.ts` grade it, because the model must never grade its own question. The assertion is binary and narrow — a tool call happened and a grade came back — which is exactly what PROV-11 claims and no more.

## Flagged assumptions (spec-less edge probe — surfaced, not silently dropped)

**FA-03 (PROV-11).** The deterministic edge probe classified PROV-11 as `unclassified` and left it `unresolved`: it could not establish which behaviour-shape edges apply to "a smoke test proving the chosen model can run the method". Per the spec-less fallback protocol an `unclassified` row is never auto-resolved with a backstop, so it is recorded here as an explicit planner assumption rather than authored into `must_haves.truths`. **The assumption:** the boundary cases that matter for PROV-11 are the four this plan covers — zero tool calls, a tool call whose arguments fail the full schema, nothing answering at the address, and the scratch lesson surviving a crash. If a verifier finds a fifth, that is a gap in this assumption, not in the requirement.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/api/*` | The new route is behind the same per-install token and session cookie as every other route, and resolves the learner through `learnerOf(c)` rather than from the request body. |
| Derive server → the chosen provider | One real model request per press, on the row's own driver, carrying the stored key or login. |
| Derive server → SQLite | A lesson row, its turn, its events and its usage rows are created and then removed inside one request. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-05 | Integrity (of the ledger and the Usage total) | the scratch lesson's lifecycle | medium | mitigate | `deleteLesson` is one transaction, so a crash *mid-delete* leaves nothing partial. A crash *between* the turn and the delete is the real exposure: it would leave a whole lesson with usage rows that the Usage total would count, contradicting D-14. Mitigated by the `lessons.scratch` marker (migration 8) plus `sweepScratchLessons()` on the boot pass, beside the existing stale-turn close. Asserted by a test that leaves a scratch lesson behind deliberately. |
| T-04-09 | Spoofing / Information Disclosure | `POST /api/settings/:provider/test-teaching` | high | mitigate | The scratch lesson is filed under `learnerOf(c)` and never a client-supplied learner id. The precedent is absolute: `recordUsage` reads the learner off the turn precisely so that no later phase can file a request under a learner its turn does not belong to. A request body carrying a learner field must not be honoured here. |
| T-04-10 | Information Disclosure | the fail `reason` shown on the row | medium | mitigate | A provider's error envelope can echo a key. Every sentence leaving `testTeaching` goes through `providerSentence` / `hintFor` / `unreachable` and then `safeMessage`, and the function answers rather than throws, so no sentence can bypass that chokepoint on its way to the browser. |
| T-04-11 | Denial of Service | repeated presses of `test teaching` | low | accept | Each press is one model request on the learner's own install, behind the loopback credential, and the button is disabled while a test is in flight. The owned loop's existing one-turn-per-lesson guard applies, and a scratch lesson is per-press so two presses cannot contend. No rate limit is added — this is a single-learner local process. |
</threat_model>
