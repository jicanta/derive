## Phase Goal

**As a** learner, **I want to** run Derive free and offline on a local model without the method silently degrading, prove any chosen model runs the method before I invest a session, and see what learning has cost across every provider, **so that** I am taught the Derive way on whatever model I have access to, with nothing lost between providers.

This plan delivers the third clause: what learning has cost, across every provider, on one page.

<objective>
Add the Usage page: a running total for this learner, by provider, model and lesson, with tokens-only lines where there is no money.

Purpose: Phase 3 put a per-lesson cost in the lesson header. The missing half is the running total across every provider — the thing that lets a learner answer "what has this cost me" without opening eleven lessons. It needs no new table, no migration and no new formatter: `listUsage({ learner })` is already an indexed read, the row already carries `driver`, `model`, `lesson_id`, `cost_source` and the five token counts denormalised, and `costOf` / `costLabel` / `weakestSource` already produce every string the approved UI-SPEC locks.

Output: `server/src/usage.ts` grouping and formatting server-side; `GET /api/usage` scoped to the resolved learner; `web/src/pages/Usage.tsx` rendering those strings; the `/usage` route; and the link from Settings that is the only way in.
</objective>

## Design notes the executor must not re-decide

**No migration, and no new formatter.** `usage_learner (learner_id, ts)` already indexes this page's only filter. `costOf` already prices a row set and `costLabel` already produces `about $X.XX billed` / `under $0.01 estimated` / `not billed` / `not reported`, with the under-half-a-cent boundary on the `about` side so a learner never reads `$0.00`. The approved UI-SPEC is explicit: the label vocabulary is fixed by `cost.ts` and must not fork, money is produced once server-side, and the page must call the same formatter and never re-format a number. So `/api/usage` returns **strings** and `Usage.tsx` prints them.

**Why a new module rather than `drivers/api.ts`.** `lessonCost` lives in `drivers/api.ts` because `cost.ts` is pure by design (no SQL, no clock) and `index.ts` starts a server. The learner-total aggregate has the same constraint and the same reason, and putting it in its own `server/src/usage.ts` keeps it out of the turn loop's file — which also keeps this plan's files disjoint from plan 04-04's.

**The provider word on a local line.** The ledger's `driver` column is the catalogue `ProviderId` — `lmstudio`, `llamacpp` — and the UI-SPEC fixes the rendered word as `lm studio` / `llama.cpp` so non-Ollama local usage is not mislabelled as `ollama`. Lowercase through `labelOf`; never print the raw id.

**A llama.cpp model id can be a filesystem path.** Its default `id` is the model file's path unless the server was started with an alias, so a line must truncate with the full value in `title` — otherwise a learner's home directory widens the layout. The UI-SPEC already requires this for both the Settings row and the Usage line.

## Flagged assumptions (spec-less edge probe — surfaced, not silently dropped)

**FA-05 (COST-03).** The deterministic edge probe classified COST-03 as `unclassified` and left it `unresolved`: it could not establish which data-shape edges apply to "a running total per learner, by provider, model and lesson, with tokens-only lines". Per the spec-less fallback protocol an `unclassified` row is never auto-resolved with a backstop, so it is recorded here as an explicit planner assumption rather than authored into `must_haves.truths`. **The assumption:** the boundary cases that matter for COST-03 are the six this plan tests — no rows at all, exactly one row, a lesson whose rows are all `subscription`, a lesson mixing `table` and `subscription`, a row with null token counts, and a total under half a cent. If a verifier finds a seventh, that is a gap in this assumption, not in the requirement.

**Research assumption A2, carried.** Whether llama.cpp and LM Studio report a `usage` object on the **streaming** path when `@ai-sdk/openai-compatible` sends `stream_options: { include_usage: true }` was not exercised — only the non-streaming case is verified. If they do not, local lines read `not reported` instead of tokens. That degrades honestly: the UI-SPEC already covers that state and forbids a `$0.00` in its place. Resolvable only with a live local server, so it is a UAT item on Task 2 rather than a blocker.
