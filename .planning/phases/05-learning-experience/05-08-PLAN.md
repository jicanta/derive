<decisions_resolved_here>
- **The project's "tool set must match in four places" directive is stale** and must not be followed literally. The foundation phase replaced the three hand-written copies with one registry projected onto four surfaces and froze it with a committed snapshot. `due` is therefore **one registry entry** — plus five pinned numbers and one generated file that move with it. D-05's claim that the four-place rule does not apply is right in effect, because an MCP-only surface keeps the tool out of the tutor's list, the in-process agent and the HTTP action switch; it is wrong in cost, and the cost is this task.
- **`/derive:due` is kept out of the method render targets (RESEARCH Pitfall 8).** The renderer computes an allowed-tools line as the registry minus a declared exclusion map and hard-fails on a target with no declared exclusions, so adding the new command as a target would mean writing a 22-key exclusion map to express "one tool". Instead the command's frontmatter carries a **hand-written single-tool** line. That is also the safer default: a hand-written line cannot silently widen when a tool is added to the registry later, whereas a rendered one would. The drift gate only checks declared targets, so leaving the new file out of them neither breaks it nor is broken by it. A source assertion in this plan is what keeps the hand-written line honest.
- **The two shipped commands each gain a `due` exclusion.** Their lines are rendered as the registry minus their exclusions, so without this `/derive:learn` and `/derive:review` would both silently gain permission to call the new tool. With it, both files render byte-identically to what is committed today. This is the single most likely thing to be missed, because the symptom is a passing render with a widened surface.
- **The Codex sibling is a sibling, not a flag (D-05 discretion).** A separate skill directory mirroring the review skill, with its manifest declaring the same MCP tool dependency, and **no rendered method region** — a one-call read needs no method text, so no fifth method surface is owed and the drift gate stays out of it.
- **No status label (RESEARCH Pitfall 2 corollary).** The registry snapshot asserts the added status-line set is exactly the owned loop's two web tools. A label on the new tool would fail that assertion by design, and correctly: the status vocabulary is per-tutor-tool, and this is a learner-facing read.
- **The output shape (D-05 discretion).** The three states the copy contract fixes, reusing the shipped Atlas overdue vocabulary so the terminal and the Atlas cannot disagree. The same strings serve both terminals.
</decisions_resolved_here>
